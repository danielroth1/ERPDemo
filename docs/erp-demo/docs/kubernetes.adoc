== Kubernetes in the context of this architecture

Kubernetes is the deployment platform that turns the system from a set of locally running processes into a cluster of independently managed services. For teams new to the technology, the most useful mental model is simple: a *Deployment* keeps pods running, a *Service* gives those pods a stable network identity, and an ingress or gateway publishes selected routes to the outside world. Everything else in the platform builds on those foundations.

This ERP demo uses Kubernetes because the application is already shaped like a cluster-native system. Services are independently deployable, each service owns its own configuration, observability is centralized, and asynchronous infrastructure such as Kafka and RabbitMQ fits naturally into a shared platform. The repository uses a common manifest base plus overlays so the same architecture can target local clusters, private k3s environments, and AKS with environment-specific changes layered on top.

== Applying the pattern

The core implementation pattern is straightforward: package each service as a container, deploy it with a Deployment, expose it with a Service, and route public traffic through a gateway or ingress. A minimal example for a backend service looks like this:

Representative source: {repo-base}/infrastructure/k8s/base/inventory.yaml#L1[infrastructure/k8s/base/inventory.yaml#L1]

[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
	name: inventory
spec:
	replicas: 2
	selector:
		matchLabels:
			app: inventory
	template:
		metadata:
			labels:
				app: inventory
		spec:
			containers:
				- name: inventory
					image: ghcr.io/example/inventory:1.0.0
					ports:
						- containerPort: 8080
					env:
						- name: ASPNETCORE_URLS
							value: http://+:8080
---
apiVersion: v1
kind: Service
metadata:
	name: inventory
spec:
	selector:
		app: inventory
	ports:
		- port: 80
			targetPort: 8080
----

In this repository, the gateway remains the main public entry point, so frontend code should still talk to one stable base URL rather than directly to internal services. That keeps service discovery inside the cluster where it belongs.

Representative source: {repo-base}/frontend/src/services/api-base-url.ts#L1[frontend/src/services/api-base-url.ts#L1]

[source,typescript]
----
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL ?? 'https://erp.example.com';

const response = await fetch(`${apiBaseUrl}/api/v1/products`);
const products = await response.json();
----

For local experimentation, it is common to apply an overlay or use a tool such as Skaffold to shorten the build-and-deploy loop, but the underlying Kubernetes concepts stay the same.

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Operational consistency*: deployments, scaling, health probes, and service discovery follow one platform model.
* *Good fit for microservices*: independent services can scale and restart without bringing down the whole system.
* *Environment layering*: overlays make it possible to adapt one manifest base to several runtimes.
|
* *Steep learning curve*: debugging pods, networking, and rollout behavior is harder than running local processes.
* *More moving parts*: ingress, secrets, storage, and service discovery add operational depth.
* *Inner-loop cost*: build and deploy cycles are slower than plain local development unless extra tooling is added.
|===
