== Distributed Workflows with Sagas

A saga is a sophisticated pattern for managing complex business workflows that span multiple independent microservices. In traditional monolithic architectures, these workflows are often handled using large, single-database transactions that guarantee ACID (Atomicity, Consistency, Isolation, Durability) properties. However, when transitioning to decentralized microservices, relying on remote distributed transactions using concepts like two-phase commit (2PC) introduces severe latency, performance bottlenecks, and single points of failure.

Sagas solve this by explicitly breaking the workflow down into a sequential series of local database transactions or steps. If one step in the sequence fails—such as a failure to charge a credit card after reserving an item—the saga executes "compensating actions" to gracefully undo or reverse the preceding successful steps (like releasing the inventory reservation). This orchestration creates robust, predictable models for handling eventual consistency across bounded contexts.

== Orchestrating the Purchase Flow

The orchestration service maintains standard saga state machines. The purchase flow is the clearest example because it touches the frontend, orchestration, inventory, financial processing, and the message brokers used to coordinate the workflow.

dotgraph::./diagrams/purchase-saga.dot[caption="Purchase saga overview",max-width=980,engine=dot]

State machines govern these flows and ensure states are saved asynchronously (typically to PostgreSQL with persistence tools like Entity Framework Core), guaranteeing that workflows survive process restarts.

Representative source: {repo-base}/services/orchestration/Orchestration/Program.cs#L105[services/orchestration/Orchestration/Program.cs#L105]

[source,csharp]
----
// The Orchestrator registers the generic state machine against a persistent database.
// This allows the saga instances to be queried or resumed across reboots.
x.AddSagaStateMachine<OrderStateMachine, OrderState>()
    .EntityFrameworkRepository(r =>
    {
        // Leveraging EF Core to store correlation IDs and the workflow's current state.
        r.ExistingDbContext<PlatformOrchestrationDbContext>();
        r.UsePostgres();
    });
----

Client initialization acts as the launch point for a saga. By emitting an event or calling the orchestration orchestrator API point, a frontend client effectively instantiates a new saga instance.

Representative sources: {repo-base}/frontend/src/services/shop.service.ts#L66[frontend/src/services/shop.service.ts#L66] and {repo-base}/frontend/src/generated/clients/orchestration/api/v1/shop/purchase/index.ts#L18[frontend/src/generated/clients/orchestration/api/v1/shop/purchase/index.ts#L18]

[source,typescript]
----
// The frontend starts the saga asynchronously by initiating the purchase command.
// We pass the required initial metadata so the StateMachine has context to execute 
// all subsequent workflow steps across diverse microservices.
async executePurchaseCommand(productId: string, quantity: number = 1) {
  return await this.apiClient.v1.orders.checkout
    .byProductId(productId)
    .post({ queryParameters: { quantity } });
}
----

== Analysis

Moving away from blocking synchronous communication to saga-driven event orchestration is a paradigm shift that solves deep distributed challenges but requires rigorous engineering discipline.

[cols="1a,1a", options="header"]
|===
| Advantages | Disadvantages

| 
* *Long-Running Process Resilience*: Workflows span temporal boundaries gracefully, surviving transient network errors and restarts without locking distributed databases.
* *Service Independence*: Services retain data isolation and high throughput because they perform fast local transactions instead of blocking distributed ones.
* *Failure as a First-Class Concept*: Compensation models force teams to proactively design error handling natively within the workflow.
| 
* *High Complexity*: Orchestration logic requires rigorous state management. It is inherently harder to debug a sequence of asynchronous compensating events than a simple synchronous HTTP chain.
* *Eventual Consistency Guarantees*: A system midway through a saga exposes intermediate data fragments to consumers.
* *Requires Idempotency*: System APIs and event consumers must handle exact duplicate messages flawlessly ensuring side-effects happen only once.
|===
