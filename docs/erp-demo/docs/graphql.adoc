== Why GraphQL exists alongside REST

GraphQL is useful when the client needs flexible read models rather than rigid endpoint-specific response shapes. In a system like this ERP demo, some screens are simple enough for REST, but others need nested data, optional fields, filtered collections, paging, and live updates without forcing the backend to create a dedicated endpoint for every UI variation. GraphQL addresses that by letting the client describe the data shape it wants while the server controls how that data is resolved.

That does not make GraphQL a universal replacement for REST. In this architecture it is primarily a read-side tool. The most successful GraphQL usage in real projects usually appears where the frontend benefits from flexible composition and where the server team is willing to invest in projection, batching, and query-governance discipline. This repository follows that pattern in inventory, sales, and dashboard scenarios.

== Applying GraphQL in code

On the server, a useful setup combines the GraphQL schema, EF Core projections, filtering, and DataLoader-based batching. That prevents the API from becoming flexible but inefficient.

Representative source: {repo-base}/services/inventory/InventoryManagement/Program.cs#L70[services/inventory/InventoryManagement/Program.cs#L70]

[source,csharp]
----
builder.Services
    .AddGraphQLServer()
    .AddQueryType<Query>()
    .AddTypeExtension<ProductQueries>()
    .AddProjections()
    .AddFiltering()
    .AddSorting()
    .AddDataLoader<ProductDocumentsByProductIdDataLoader>();

public sealed class ProductQueries
{
    [UseOffsetPaging(DefaultPageSize = 20, IncludeTotalCount = true)]
    [UseProjection]
    [UseFiltering]
    [UseSorting]
    public IQueryable<Product> GetProducts([Service] InventoryDbContext dbContext)
        => dbContext.Products.AsNoTracking().OrderBy(product => product.Name);
}

When nested data is involved, a DataLoader batches lookups so the resolver layer does not create one database query per row.

Representative source: {repo-base}/services/inventory/InventoryManagement/GraphQL/DataLoaders/ProductDocumentsByProductIdDataLoader.cs#L12[services/inventory/InventoryManagement/GraphQL/DataLoaders/ProductDocumentsByProductIdDataLoader.cs#L12]

[source,csharp]
----
public sealed class ProductDocumentsByProductIdDataLoader
    : BatchDataLoader<string, IReadOnlyList<ProductDocument>>
{
    protected override async Task<IReadOnlyDictionary<string, IReadOnlyList<ProductDocument>>> LoadBatchAsync(
        IReadOnlyList<string> keys,
        CancellationToken cancellationToken)
    {
        await using var dbContext = await _dbContextFactory.CreateDbContextAsync(cancellationToken);

        var documents = await dbContext.ProductDocuments
            .Where(document => keys.Contains(document.ProductId))
            .ToListAsync(cancellationToken);

        return keys.ToDictionary(
            key => key,
            key => (IReadOnlyList<ProductDocument>)documents.Where(document => document.ProductId == key).ToList());
    }
}
----

On the client, GraphQL is typically initialized through Apollo Client or another GraphQL client, then used with strongly named operations.

Representative source: {repo-base}/frontend/src/services/apollo.client.ts#L87[frontend/src/services/apollo.client.ts#L87]

[source,typescript]
----
const inventoryGraphQlClient = new ApolloClient({
  uri: `${getApiBaseUrl()}/graphql/inventory`,
  cache: new InMemoryCache(),
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

const { data } = await inventoryGraphQlClient.query({
  query: gql`
    query GetProductWithDocuments($id: String!) {
      product(id: $id) {
        id
        name
        price
        documents {
          id
          originalFileName
        }
      }
    }
  `,
  variables: { id: productId },
});

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Flexible read models*: screens can ask for exactly the fields they need.
* *Strong fit for nested UI data*: related entities can be composed in one round trip.
* *Projection and batching can be efficient*: the backend can avoid over-fetching when implemented carefully.
|
* *More complex than REST*: schema design, query governance, and resolver performance need active care.
* *Poor defaults can be expensive*: missing DataLoader or projection rules quickly lead to N+1 problems.
* *Caching is less obvious*: HTTP-level caching is harder than with simple resource endpoints.
|===
