== PostgreSQL as the durable system of record

PostgreSQL is the primary relational database used across the system. It stores transactional business data, read-model data, and saga state. That choice is significant because the ERP domain is full of entities that benefit from relational guarantees: products, users, budgets, stock movements, financial transactions, and workflow state all require consistency, indexing, and a well-understood query model.

In a microservice architecture, the key principle is not simply "use PostgreSQL". The more important rule is "each service owns its own schema or database". This repository follows that pattern by letting each service manage its own logical database and migrations. That preserves service autonomy and reduces the temptation to solve cross-service needs with direct SQL joins between unrelated domains.

== Applying the pattern

At the infrastructure level, PostgreSQL can host several logical databases while still being one shared server in development. That keeps local setup simple without abandoning data ownership.

[source,yaml]
----
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: erp
      POSTGRES_PASSWORD: changeme
      POSTGRES_MULTIPLE_DATABASES: users,inventory,sales,financial,dashboard,orchestration
    ports:
      - "5432:5432"
----

Application code should then read a service-specific connection string and use migrations to keep the schema in sync.

[source,csharp]
----
var connectionString = builder.Configuration.GetConnectionString("financial-db")
    ?? throw new InvalidOperationException("The financial database is not configured.");

builder.Services.AddDbContext<FinancialDbContext>(options =>
    options.UseNpgsql(connectionString));
----

When database design becomes explicit, teams can also explain their model clearly. A table definition for a financial transaction might look like this:

[source,sql]
----
CREATE TABLE financial_transactions (
    id uuid PRIMARY KEY,
    account_id uuid NOT NULL,
    amount numeric(18,2) NOT NULL,
    currency_code varchar(3) NOT NULL,
    created_at_utc timestamp with time zone NOT NULL
);

CREATE INDEX ix_financial_transactions_account_id
    ON financial_transactions (account_id);
----

The browser never connects to PostgreSQL directly. It consumes data through REST, GraphQL, and real-time endpoints exposed by backend services.

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Strong transactional model*: ideal for financial data, workflow state, and core business records.
* *Mature tooling*: migrations, backups, indexing, and monitoring are well understood.
* *Good fit with EF Core*: application code and relational storage integrate cleanly.
|
* *Schema evolution needs discipline*: migrations must be ordered, reviewed, and deployed carefully.
* *Shared server is not shared ownership*: each service still needs clear boundaries around its data.
* *Cross-service reporting requires design*: direct database coupling is tempting but usually the wrong solution.
|===
