== System Architecture Overview

Designing a modern distributed system involves making critical decisions about how decoupled services communicate and share data. This architecture uses a polyglot integration pattern—meaning it embraces several distinct communication styles, utilizing each where it naturally fits the system's technical requirements and the frontend's functional needs. By combining HTTP APIs with asynchronous message-oriented middleware and bi-directional streaming protocols, the architecture optimizes resilience, responsiveness, and horizontal scalability across its subdomains.

== Request Styles and Domain Modality

One of the easiest design mistakes when building a polyglot system is attempting to solve every communication challenge with a standard synchronous REST API. The architecture inside a complex software application necessitates varying request-response paradigms corresponding to different non-functional demands (throughput, consistency, real-time availability).

This system splits integration styles deliberately depending on the scenario's demands:
* *REST* remains the default for standard Command Query Responsibility Segregation (CQRS) flows involving direct, synchronous write operations and foundational CRUD endpoints where predictable schema contracts naturally fit.
* *GraphQL* orchestrates complex graph-like read patterns. This pattern excels when the frontend must query deeply nested data structures spanning multiple entities without causing "over-fetching" or triggering the N+1 execution problem.
* *SignalR / WebSockets* pushes real-time telemetry, live alerts, and dashboard updates from the server layers down to the web client, bypassing the latency of periodic HTTP polling.
* *Event-Driven Messaging (Kafka & RabbitMQ)* anchors the asynchronous backbone of the microservice ecosystem. Kafka broadcasts durable, replayable facts about the business domain (e.g., `OrderPlaced`), allowing downstream services to independently consume and interpret facts. RabbitMQ reliably queues specific inter-service workflow commands for immediate action, providing robust routing guarantees during distributed orchestrations (Sagas).

== Design Analysis

Implementing diverse networking layers significantly impacts the system lifecycle, influencing how teams write code, monitor infrastructure, and design error-handling strategies.

[cols="1a,1a", options="header"]
|===
| Architectonic Strengths | Design Trade-Offs

| 
* *Optimized Sub-Domain Boundaries*: Each service independently scales and operates with the technology pattern that suits its precise workload (e.g., using messaging for asynchronous tasks vs routing GraphQL queries for heavy reads).
* *Graceful Degradation Component Resilience*: Core services leveraging decoupled event buses (Sagas) avoid catastrophic failures that typically occur alongside massive blocking API calls traversing multiple services synchronously.
* *Rich Frontend Capability*: Using SignalR and GraphQL gives client applications the flexible tools required to construct deeply interactive user experiences with extremely efficient data loading.
| 
* *Diagnostic Complexity*: Debugging requests tracing across API gateways, asynchronous message queues, and back into synchronous databases is notoriously harder than diagnosing simple application monoliths.
* *Eventual Consistency Hurdles*: Engineers face challenges maintaining logical coherence across databases when using asynchronous messaging formats since distributed commits are abandoned.
* *Operational Overhead*: DevOps and infrastructure teams must maintain complex hybrid networks and multiple service types (e.g., Redis, MinIO, RabbitMQ, Kafka) over standard SQL servers.
|===
