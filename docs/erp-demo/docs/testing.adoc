== Why distributed systems need several test layers

A distributed system cannot be tested well with one technique alone. Unit tests are fast and precise, but they do not prove that ASP.NET Core, EF Core, message brokers, and the frontend are wired together correctly. End-to-end tests are realistic, but they are slower and more brittle. The right strategy is therefore layered: use the cheapest test that can answer the question, and only move to a heavier layer when the lower one cannot prove the behavior.

That principle matters even more in this ERP demo because the system spans synchronous APIs, asynchronous messaging, databases, and browser behavior. A saga transition, a React loading state, a database migration, and a full purchase journey are not the same testing problem. Treating them as if they were leads either to over-mocked tests that prove too little or to expensive system tests that teams stop running regularly.

== Applying the test pyramid

The repository uses four complementary layers, each answering a different risk.

Unit tests:: Use these for focused business rules, pure services, and saga transitions. They should be fast and narrow.

[source,csharp]
----
await _harness.Bus.Publish(new SubmitPurchase
{
    CorrelationId = correlationId,
    ProductId = "prod-1",
    Quantity = 5,
});

(await _sagaHarness.Exists(correlationId, state => state.ReservingStock, TimeSpan.FromSeconds(5)))
    .Should().NotBeNull();
----

Component tests:: Use these for React screens and UI state transitions with mocked dependencies.

[source,typescript]
----
vi.mock('../../services/inventory.service', () => ({
  inventoryService: {
    getProducts: vi.fn().mockResolvedValue({ items: [{ id: '1', name: 'Keyboard' }], totalCount: 1 }),
  },
}));

renderWithProviders(<InventoryPage />);
expect(screen.getByText('Keyboard')).toBeInTheDocument();
----

Integration tests:: Use these when the real application host, database wiring, or messaging infrastructure integration must be validated.

[source,csharp]
----
var factory = new WebApplicationFactory<Program>()
    .WithWebHostBuilder(builder =>
    {
        builder.UseEnvironment("Testing");
        builder.ConfigureServices(services =>
        {
            services.AddDbContext<InventoryDbContext>(options =>
                options.UseNpgsql(testDatabaseConnectionString));

            services.AddMassTransitTestHarness();
        });
    });
----

System tests:: Use these for end-user flows in a real browser with Playwright or a similar tool.

[source,typescript]
----
export default defineConfig({
  testDir: './tests',
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:5173',
  },
  projects: [
    { name: 'chromium' },
    { name: 'firefox' },
    { name: 'webkit' },
  ],
});
----

[cols="1,3",options="header"]
|===
| Question | Best starting layer

| Is one workflow transition correct?
| Unit test

| Does one React screen show the correct state?
| Component test

| Does this service boot and talk to its database correctly?
| Integration test

| Can a user complete the full journey in a browser?
| System test
|===

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Risk is tested at the right level*: business rules, framework wiring, and user journeys each get the right kind of proof.
* *Faster feedback overall*: most regressions can be caught before the slowest tests are needed.
* *Better confidence in distributed behavior*: messaging, persistence, and browser flows are all covered in the right place.
|
* *More tooling to maintain*: test harnesses, browsers, databases, and mock layers all need care.
* *Poor boundaries create duplication*: the same scenario can end up rewritten at every layer if the strategy is unclear.
* *System tests remain expensive*: they are necessary, but they should not carry the entire quality burden.
|===
