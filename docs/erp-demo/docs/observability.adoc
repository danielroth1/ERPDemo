== Observability as a runtime design concern

Observability is the ability to understand what the system is doing while it is running, especially when the answer is not obvious from one log line or one failed request. In a distributed architecture like this ERP demo, that matters far more than in a monolith because a single business action can cross the gateway, several backend services, two message brokers, and multiple databases before it completes. Metrics tell you *that* something is wrong, logs help explain *what* happened, and traces reveal *where* time was spent across service boundaries.

The stack used here follows the common three-signal model. OpenTelemetry instrumentation emits telemetry from the services, Prometheus stores metrics, Loki stores logs, Tempo stores traces, and Grafana ties the information together. The important lesson is not the brand names themselves; it is the correlation model. A healthy observability setup lets an operator move from an elevated error rate, to the affected logs, to the trace that shows which downstream dependency actually failed.

== Applying the pattern

Good observability starts in application code. Services should register standard HTTP instrumentation, client instrumentation, and any custom activity sources that represent business or messaging behavior.

[source,csharp]
----
builder.Services.AddOpenTelemetry()
    .WithMetrics(metrics =>
    {
        metrics.AddAspNetCoreInstrumentation()
               .AddHttpClientInstrumentation()
               .AddMeter("MassTransit");
    })
    .WithTracing(tracing =>
    {
        tracing.AddAspNetCoreInstrumentation()
               .AddHttpClientInstrumentation()
               .AddSource("InventoryService")
               .AddSource("MassTransit");
    });
----

Once tracing is enabled, feature code can create spans around important operations so cross-service workflows remain understandable.

[source,csharp]
----
private static readonly ActivitySource ActivitySource = new("InventoryService");

public async Task ReserveStockAsync(string productId, int quantity, CancellationToken cancellationToken)
{
    using var activity = ActivitySource.StartActivity("ReserveStock");
    activity?.SetTag("product.id", productId);
    activity?.SetTag("stock.quantity", quantity);

    var product = await _dbContext.Products.SingleAsync(x => x.Id == productId, cancellationToken);
    product.Reserve(quantity);
    await _dbContext.SaveChangesAsync(cancellationToken);
}
----

The infrastructure side then needs a collector or pipeline that accepts OTLP data and forwards it to the right storage backends.

[source,hcl]
----
otelcol.receiver.otlp "services" {
  grpc {
    endpoint = "0.0.0.0:4317"
  }

  output {
    logs   = [otelcol.exporter.loki.default.input]
    traces = [otelcol.exporter.otlp.tempo.input]
  }
}
----

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Cross-service visibility*: traces and correlated logs make asynchronous workflows debuggable.
* *Faster diagnosis*: metrics reveal symptoms quickly and traces narrow the failing dependency.
* *Operational maturity*: the system becomes measurable rather than anecdotal.
|
* *Instrumentation effort is real*: telemetry is only useful when services emit meaningful spans, tags, and structured logs.
* *The stack itself must be operated*: Loki, Tempo, Grafana, and collectors need care just like business services do.
* *Signal overload is possible*: too much noisy telemetry can be as unhelpful as too little.
|===
