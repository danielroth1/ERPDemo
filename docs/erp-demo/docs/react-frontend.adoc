== Overview

The frontend is a skill:React[] and skill:TypeScript[] single-page application built with Vite. From the user's perspective it feels like one web app, but it talks to several backend capabilities through the API gateway and service-specific clients.

IMPORTANT: The browser never talks directly to PostgreSQL, Kafka, RabbitMQ, or MinIO. Those systems stay behind backend APIs.

== Frontend Foundation

=== Introduction

React is responsible for UI rendering, local component state, forms, navigation, and user interaction. Vite provides the development server and build pipeline.

=== Setup Example

[source,bash]
----
cd frontend
npm install
npm run dev
----

=== Base URL Example

[source,typescript]
----
import { getApiBaseUrl } from './api-base-url';

const baseUrl = getApiBaseUrl();
console.log(baseUrl);
----

=== Advantages

* Fast local development with Vite.
* Clean separation between UI and backend services.
* React tooling works well with REST, GraphQL, and real-time patterns.

=== Disadvantages

* Frontend state, loading, and authentication flows still need discipline.
* Mixing several API styles can become confusing if the rules are not explicit.

== Real-Time Updates

=== Introduction

The frontend currently uses two real-time mechanisms:

* SignalR for hub-based dashboard updates.
* GraphQL subscriptions for pushed GraphQL events.

=== Client Setup

[source,typescript]
----
const wsUrl = `${getApiBaseUrl()}/dashboardHub`;
await signalRService.connect(wsUrl, token);
----

=== Simple Example

Dashboard users can receive low-stock alerts or updated KPI data without manually refreshing the page because the backend pushes updates to connected clients.

=== Advantages

* Better user experience for dashboards and monitoring screens.
* Reduces wasteful polling.

=== Disadvantages

* Reconnection and authorization logic add complexity.
* Debugging intermittent real-time issues is harder than debugging plain HTTP.

== A Practical Frontend Pattern In This Repository

One screen often mixes several techniques at the same time:

* GraphQL for a flexible read model.
* REST for create or update actions.
* SignalR or subscriptions for background updates.

That combination is normal in this codebase. The important rule is not to force one technology everywhere, but to match the user interaction to the right backend pattern.
