== Why MassTransit is central to the architecture

MassTransit is the messaging abstraction that keeps the application's broker code from fragmenting into transport-specific plumbing. That matters in this ERP demo because the system uses both RabbitMQ and Kafka, and it also relies on higher-level messaging patterns such as retries, outbox delivery, test harnesses, and saga state machines. Without a consistent abstraction, every service would need to solve connection management, endpoint naming, retry behavior, and message dispatching in slightly different ways.

The real benefit is not simply convenience. MassTransit gives the codebase a common mental model for asynchronous workflows. Whether a service is sending a RabbitMQ command, publishing a Kafka event, or progressing a saga, the surrounding application code stays recognizable. That consistency reduces accidental complexity, especially when the system grows and more teams contribute to the messaging layer.

== Applying the pattern

A useful baseline setup configures endpoint naming, consumers, persistence-backed outbox behavior, and transport-specific details in one place. The example below captures the essential structure:

Representative source: {repo-base}/services/inventory/InventoryManagement/Program.cs#L96[services/inventory/InventoryManagement/Program.cs#L96]

[source,csharp]
----
builder.Services.AddMassTransit(x =>
{
    x.SetKebabCaseEndpointNameFormatter();

    x.AddConsumer<ReserveStockConsumer>();
    x.AddConsumer<CreatePurchaseTransactionConsumer>();

    x.AddEntityFrameworkOutbox<AppDbContext>(outbox =>
    {
        outbox.UsePostgres();
        outbox.UseBusOutbox();
        outbox.QueryDelay = TimeSpan.FromMilliseconds(100);
    });

    x.UsingRabbitMq((context, cfg) =>
    {
        cfg.Host(builder.Configuration["RabbitMQ:Host"], host =>
        {
            host.Username(builder.Configuration["RabbitMQ:Username"]);
            host.Password(builder.Configuration["RabbitMQ:Password"]);
        });

        cfg.ConfigureEndpoints(context);
    });
});
----

Once configured, application code should depend on interfaces such as `IPublishEndpoint`, `ISendEndpointProvider`, or typed producers instead of talking directly to the broker SDK. That keeps business logic focused on intent.

Representative source: {repo-base}/services/orchestration/Orchestration/Controllers/ShopController.cs#L51[services/orchestration/Orchestration/Controllers/ShopController.cs#L51]

[source,csharp]
----
public sealed class PurchaseWorkflowStarter
{
    private readonly IPublishEndpoint _publishEndpoint;

    public PurchaseWorkflowStarter(IPublishEndpoint publishEndpoint)
    {
        _publishEndpoint = publishEndpoint;
    }

    public Task StartAsync(Guid correlationId, string productId, int quantity, CancellationToken cancellationToken)
    {
        return _publishEndpoint.Publish(new SubmitPurchase
        {
            CorrelationId = correlationId,
            ProductId = productId,
            Quantity = quantity,
        }, cancellationToken);
    }
}
----

The frontend has no direct MassTransit integration. It benefits indirectly because backend messaging becomes more reliable, testable, and easier to evolve.

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *One programming model for many messaging patterns*: commands, events, sagas, retries, and tests stay coherent.
* *Outbox and retry support are built in*: reliability patterns become easier to apply consistently.
* *Transport details stay contained*: application code depends on messaging intent rather than low-level broker APIs.
|
* *You still need transport knowledge*: RabbitMQ and Kafka semantics do not disappear just because the API is unified.
* *Framework concepts add learning cost*: consumers, state machines, riders, and outbox behavior need to be understood.
* *Misconfiguration can be subtle*: endpoint naming, retries, and persistence behavior must be reviewed carefully.
|===
