== What this documentation is trying to teach

ERPDemo is a microservice-based ERP sample that is meant to be read as both a concrete project and a technology case study. The system is split into business-focused services such as inventory, sales, financial processing, dashboard analytics, and orchestration rather than being implemented as one large backend. That architectural split is deliberate: it makes the project a useful example of how modern distributed systems combine HTTP APIs, asynchronous messaging, object storage, observability, and frontend composition in one runtime.

For readers who are new to these technologies, the most important mindset is to treat the project as a set of cooperating layers rather than as a single web application. The browser talks to the gateway, the gateway routes to internal services, services own their own data, and long-running workflows continue over message brokers after the original HTTP request has completed. Once that mental model is clear, the individual chapters become much easier to understand.

== System at a glance

[cols="1,3",options="header"]
|===
| Area | Current implementation

| Frontend
| React, TypeScript, Vite, Apollo Client, generated REST clients, SignalR

| Edge
| ASP.NET Core API Gateway with YARP reverse proxy, JWT authentication, rate limiting, and metrics

| Business services
| User Management, Inventory, Sales, Financial, Dashboard, Orchestration

| Databases
| PostgreSQL with one logical database per service

| Messaging
| Kafka for domain events and RabbitMQ for workflow commands

| Workflow coordination
| MassTransit saga state machines in the orchestration service

| File storage
| MinIO as an S3-compatible object store for product assets and documents

| Real-time updates
| SignalR and GraphQL subscriptions

| Observability
| OpenTelemetry, Prometheus, Grafana, Alloy, Loki, and Tempo

| Local orchestration
| Docker Compose and .NET Aspire

| Cluster deployment
| Local Kubernetes, private k3s, and Azure AKS overlays
|===

The easiest beginner model is this: one React application talks to one public backend entry point, that entry point routes to specialized services, and not every interaction is synchronous HTTP. Some business actions become events, some become queued commands, and some become long-running sagas. That is the central trade-off of microservice architecture: clearer service boundaries and deployment flexibility in exchange for more moving parts and more distributed-systems concerns.

== How to read the project

The service split follows business boundaries. Inventory owns products and stock, financial owns accounting rules, dashboard owns read models and live analytics, and orchestration owns cross-service workflows that would otherwise be awkward to embed in a single business service. That keeps each service easier to reason about locally, but it also introduces eventual consistency, retries, compensation, message ordering, and monitoring concerns that a monolith can often postpone.

If you want to build an accurate mental model quickly, this reading order works well: start with the architecture overview, then the frontend and API chapters, then the backend/runtime chapters, then the messaging and saga chapters, and finally the deployment and debugging chapters. Throughout the documentation, three rules are worth repeating because they explain a large share of the system behavior:

* Browsers never talk directly to PostgreSQL, Kafka, RabbitMQ, or MinIO.
* GraphQL is primarily used for flexible read models, while REST still handles many write and CRUD paths.
* Kafka and RabbitMQ solve different problems: one broadcasts facts, the other moves workflow commands.
