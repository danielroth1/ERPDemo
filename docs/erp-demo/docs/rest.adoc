== Why REST remains the default tool

REST is still the simplest and most widely useful communication style in this repository. A client sends an HTTP request to a resource-oriented endpoint and receives a structured response. That model remains valuable even in a system that also uses GraphQL and messaging because many business actions are naturally request-response operations: create a product, update a budget, retrieve the current user, or start a workflow. Those tasks benefit from explicit routes, familiar HTTP semantics, middleware support, and strong client-generation tooling.

In this ERP demo, REST is especially important on write paths and straightforward CRUD paths. The gateway routes incoming requests to the correct service, ASP.NET Core controllers implement the API surface, and the frontend often uses generated clients so it can call those endpoints with a typed developer experience. REST is not the answer to every read-model problem, but it is still the most direct way to represent transactional commands and simple resources.

== Applying REST in code

At the edge, the gateway matches public routes and forwards them to the right backend service. That keeps the browser focused on one entry point instead of many service URLs.

Representative source: {repo-base}/services/gateway/ApiGateway/appsettings.json#L38[services/gateway/ApiGateway/appsettings.json#L38]

[source,json]
----
{
  "routes": {
    "inventory-products": {
      "clusterId": "inventory",
      "authorizationPolicy": "authenticated",
      "match": {
        "path": "/api/v1/products/{**catch-all}"
      }
    }
  }
}
----

Inside the service, a controller expresses the business action in the usual ASP.NET Core way.

Representative source: {repo-base}/services/inventory/InventoryManagement/Controllers/ProductsController.cs#L142[services/inventory/InventoryManagement/Controllers/ProductsController.cs#L142]

[source,csharp]
----
[ApiController]
[Route("api/v1/products")]
public sealed class ProductsController : ControllerBase
{
    private readonly IProductService _productService;

    public ProductsController(IProductService productService)
    {
        _productService = productService;
    }

    [HttpPost]
    [Authorize]
    public async Task<ActionResult<ProductResponse>> Create(CreateProductRequest request, CancellationToken cancellationToken)
    {
        var product = await _productService.CreateAsync(request, cancellationToken);
        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }

    [HttpGet("{id}")]
    public Task<ProductResponse?> GetById(string id, CancellationToken cancellationToken)
        => _productService.GetByIdAsync(id, cancellationToken);
}
----

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Easy to reason about*: routes, verbs, and status codes are familiar to most teams.
* *Strong fit for commands and CRUD*: transactional operations map naturally to endpoints.
* *Excellent tooling*: gateways, client generators, middleware, caching, and observability all work well with HTTP.
|
* *Complex screens may need many calls*: a pure REST design can under-serve read-heavy UIs.
* *Over-fetching is common*: fixed response shapes do not always match the needs of a specific screen.
* *Cross-service composition gets awkward*: read models that span many services often need something more flexible.
|===
