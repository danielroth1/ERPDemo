== RabbitMQ as the command channel for workflows

RabbitMQ is used here for messages that represent an instruction or a unit of work that another service should perform next. That makes it fundamentally different from Kafka. If Kafka answers the question "what already happened?", RabbitMQ answers the question "what should happen now?". In saga-driven workflows, that distinction is extremely useful because orchestration logic often needs to queue the next step, retry when a service is temporarily unavailable, and keep commands isolated from public HTTP request lifetimes.

This ERP demo uses RabbitMQ heavily in purchase and return workflows. Commands such as reserve stock, release reservation, create transaction, or void transaction move between services through the broker. That allows the workflow to continue even when the initiating HTTP request has already completed, and it keeps long-running business coordination out of the browser and out of synchronous call chains.

== Applying the pattern

RabbitMQ is typically configured through MassTransit consumers and endpoints. A service registers the message handlers it can execute, then configures retries and endpoint creation during startup.

Representative source: {repo-base}/services/orchestration/Orchestration/Program.cs#L147[services/orchestration/Orchestration/Program.cs#L147]

[source,csharp]
----
builder.Services.AddMassTransit(x =>
{
    x.AddConsumer<ReserveStockConsumer>();
    x.AddConsumer<ReleaseStockReservationConsumer>();

    x.UsingRabbitMq((context, cfg) =>
    {
        cfg.Host(builder.Configuration["RabbitMQ:Host"], host =>
        {
            host.Username(builder.Configuration["RabbitMQ:Username"]);
            host.Password(builder.Configuration["RabbitMQ:Password"]);
        });

        cfg.UseMessageRetry(retry => retry.Intervals(
            TimeSpan.FromSeconds(1),
            TimeSpan.FromSeconds(5),
            TimeSpan.FromSeconds(15)));

        cfg.ConfigureEndpoints(context);
    });
});
----

Sending a command should express clear intent and include enough correlation data for the workflow to continue safely.

Representative source: {repo-base}/services/orchestration/Orchestration/Sagas/PurchaseStateMachine.cs#L47[services/orchestration/Orchestration/Sagas/PurchaseStateMachine.cs#L47]

[source,csharp]
----
public sealed class PurchaseOrchestrator
{
    private readonly ISendEndpointProvider _sendEndpointProvider;

    public PurchaseOrchestrator(ISendEndpointProvider sendEndpointProvider)
    {
        _sendEndpointProvider = sendEndpointProvider;
    }

    public async Task RequestStockReservationAsync(Guid correlationId, string productId, int quantity, CancellationToken cancellationToken)
    {
        var endpoint = await _sendEndpointProvider.GetSendEndpoint(new Uri("queue:reserve-stock"));

        await endpoint.Send(new ReserveStock
        {
            CorrelationId = correlationId,
            ProductId = productId,
            Quantity = quantity,
        }, cancellationToken);
    }
}
----

The frontend still interacts through HTTP. It starts a business action, and RabbitMQ carries the asynchronous continuation of the workflow behind the scenes.

== Analysis

[cols="1a,1a",options="header"]
|===
| Advantages | Trade-offs

|
* *Strong fit for queued work*: commands can be retried and processed outside the original request lifetime.
* *Good workflow semantics*: saga steps map naturally to directed commands.
* *Clear separation of concerns*: browsers trigger workflows, services execute them asynchronously.
|
* *Another broker to run and monitor*: queue depth, dead letters, and consumer health become operational concerns.
* *Duplicate handling is mandatory*: commands can be retried and consumers must be idempotent.
* *Observability must be deliberate*: asynchronous command chains are harder to follow than synchronous HTTP calls.
|===
